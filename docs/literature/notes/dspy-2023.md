# DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines

- **Citation:** Khattab O, Singhvi A, Maheshwari P, et al., arXiv 2310.03714, 2023 (ICLR 2024).
- **Link:** https://arxiv.org/abs/2310.03714 · **Open access:** yes (full text read)
- **Code:** https://github.com/stanfordnlp/dspy · **Code licence:** MIT (LICENSE file checked)
- **Paper licence:** arXiv non-exclusive
- **Informs:** learning

## Mechanism
A pipeline is written as modules that each have a signature ("context, question -> answer") instead of a hand-written prompt. A "teleprompter" (optimiser) compiles the program against a training set and a metric in two stages: (1) run a teacher program on training inputs and keep traces whose final output passes the metric, giving bootstrapped demonstrations for every module, including intermediate steps with no labels; (2) treat the demonstration sets (or instructions, or finetunes) as parameters and pick among them by random search or Optuna-style search with validation. Compilation can be nested (a compiled program teaches another) and ensembled by voting. Compile time is roughly 10-20 trials over 150-300 validation examples. Runtime cost of the compiled program equals the pipeline's own calls; compiling adds nothing live.

## Evidence
GSM8K (200 train, 300 dev, 1.3k test): GPT-3.5 vanilla 25.2% test; bootstrap x2 61.7%; CoT with human demos 72.4%; CoT bootstrapped 72.9%, +ensemble 81.6%; reflection bootstrapped 76.0%. Llama2-13b-chat vanilla 9.4%; bootstrap x2 36.5%; reflection bootstrap 40.2%, +ensemble 46.9%. HotPotQA (test): GPT-3.5 multihop fewshot 31.2% EM, bootstrap 39.6%, ensemble 45.6% (on half the test set); Llama2-13b-chat multihop 31.3% to 36.4% to 41.0%. A T5-Large (770M) finetuned from a compiled teacher reached 39.3% EM dev with 200 labelled and 800 unlabelled questions. Abstract's "over 25% and 65%" are relative gains versus standard few-shot.

## Limitations
- Only two case studies (maths word problems, multi-hop QA) with exact-match metrics; no dialogue tasks.
- Gains rely on a metric that can be computed automatically; bootstrapped demos can overfit small sets.
- The paper's optimisers are bootstrapped-demo and search based; instruction-rewriting optimisers (MIPRO, GEPA) came later.
- Test numbers are single runs; one HotPotQA result uses half the test set for cost.

## For Rapport
**Verdict:** adapt. MIT. Not worth adopting the whole framework for one structured call, but the pattern is right: a signature-style output schema (reaction, intensity, behaviour, resistance, emotion, utterance) plus a metric-gated compile step, with bootstrapped good replies from the experience library as few-shot demos. Use DSPy as the harness and GEPA (which plugs into DSPy) as the optimiser in the nightly gated job; clinical facts stay outside the optimised parameters.
